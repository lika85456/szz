
# W-1-1
## front
Jaké jsou tři základní kategorie autentizace uživatele ve webových aplikacích? Vyjmenujte je.
## back
- Něco ví (knowledge-based) – např. jméno a heslo, PIN, ověřovací otázka
- Něco má (possession-based) – např. telefon, token, certifikát
- Někým je (inherence-based/biometrie) – např. otisk prstu, snímek duhovky, DNA

# W-1-2
## front
Vyjmenujte alespoň jeden příklad způsobu autentizace pro každou kategorii: "něco ví", "něco má", "někým je".
## back
- Něco ví: jméno a heslo, PIN, ověřovací otázka
- Něco má: telefon, token, certifikát
- Někým je: otisk prstu, snímek duhovky, DNA

# W-1-3
## front
Co je HTTP Basic autentizace a jak funguje?
## back
- HTTP Basic autentizace posílá uživatelské jméno a heslo zakódované v Base64 v hlavičce HTTP požadavku.
- Není šifrovaná, proto je nutné vždy použít HTTPS.
- Hlavička má tvar: Authorization: Basic base64(username:password)

# W-1-4
## front
Jaké bezpečnostní slabiny má HTTP Basic autentizace? Jaký protokol by měl být použit pro zabezpečení přenosu dat?
## back
- HTTP Basic autentizace neposkytuje šifrování, pouze základní zakódování (Base64), které lze snadno dekódovat.
- Proto je nutné použít šifrovaný přenos přes HTTPS, jinak mohou být údaje odposlechnuty.

# W-1-5
## front
Popište základní postup HTTP Digest autentizace.
## back
- Klient odešle požadavek na přihlášení.
- Server odpoví 401 Unauthorized a pošle „nonce“ (náhodný token) a další parametry.
- Klient spočítá hash (MD5) z kombinace nonce, uživatelského jména, hesla a URL a odešle výsledek serveru.
- Server ověří hash a tím i znalost hesla.
- HTTP Digest je již považován za zastaralou metodu.

# W-1-6
## front
Jaký je základní rozdíl mezi HTTP Basic a HTTP Digest autentizací?
## back
- HTTP Basic posílá přihlašovací údaje pouze zakódované (Base64), zatímco HTTP Digest posílá hash, který je vypočítán pomocí nonce, uživatelského jména, hesla a URL.
- Obě metody jsou považovány za zastaralé.

# W-1-7
## front
Proč je HTTP Digest autentizace považována za bezpečnější než HTTP Basic?
## back
- Místo přímého zasílání hesla/hash hesla klient posílá hash vypočítaný z nonce, uživatelského jména, hesla a URL.
- Heslo samotné se nikdy neposílá po síti ani v zakódované (Base64) podobě.
- Nicméně je to stejně již zastaralá metoda.

# W-1-8
## front
K čemu slouží API klíč v kontextu webových aplikací a jaké vlastnosti má mít?
## back
- API klíč slouží k autentizaci služeb nebo aplikací (nikoliv uživatele).
- Aplikace klientovi vygeneruje náhodný token, který klient používá např. v hlavičce HTTP požadavku.
- API klíč musí být:
  - Náhodný
  - Neuhodnutelný
  - Odvolatelný (token lze podle potřeby zrušit)

# W-1-9
## front
Jaký je účel OAuth protokolu?
## back
- OAuth je protokol pro autentizaci pomocí třetí strany.
- Umožňuje, aby třetí strana (např. Google, Facebook) ověřila uživatele bez toho, aby musel službě sdělit své přihlašovací údaje.

# W-1-10
## front
Vysvětlete rozdíl mezi autentizací a autorizací ve webových aplikacích.
## back
- Autentizace: Ověření identity uživatele (kdo je uživatel?)
- Autorizace: Určení oprávnění, která uživatel má (co smí uživatel dělat?)

# W-1-11
## front
Jaké jsou metody autorizace? Stručně popište role, ACL a RBAC.
## back
- Role: Staticky definované role (např. .hasRole), podle kterých jsou určována práva uživatele.
- ACL (Access Control List): Přístupová práva se přiřazují jednotlivým uživatelům pro konkrétní objekty (například soubory, sekce apod.).
- RBAC (Role Based Access Control): Uživatelé mají přiřazené role, role mají přiřazená oprávnění.

# W-1-12
## front
Vyjmenujte a krátce popište nejčastější zranitelnosti webových aplikací uvedené v materiálu.
## back
- SQL Injection: Vložení škodlivého SQL kódu do vstupu, který je následně vykonán databází.
- XSS (Cross Site Scripting): Vložení škodlivého skriptu do webové stránky, který se poté spustí v prohlížeči uživatele.
- Remote Code Execution: Útočník získá možnost spouštět libovolný kód na serveru.
- CSRF (Cross Site Request Forgery): Zneužití uživatelské relace k vykonání úkonu jménem uživatele, například zasláním obrázku s odkazem na nechtěnou operaci.

# W-1-13
## front
Co je CSRF (Cross Site Request Forgery) a jak může být zneužito ve webových aplikacích?
## back
- Útok, při kterém útočník využije relaci přihlášeného uživatele a provede nežádoucí akci jeho jménem.
- Například tím, že uživatel otevře stránku s obrázkem, jehož src je odkaz na nebezpečnou operaci, např. http://mojeaplikace.cz/transfer?amount=1000&to=mojeid

# W-1-14
## front
Uveďte zabezpečovací opatření proti SQL Injection.
## back
- Používání parametrizovaných dotazů (prepared statements)
- Ošetření vstupních dat (validace, escapování)
- Omezení práv v databázi (uživatel by neměl mít větší oprávnění, než je nutné)
- Pravidelné aktualizace softwaru

# W-1-15
## front
Uveďte základní ochranu proti XSS (Cross Site Scripting).
## back
- Escapování a validace vstupu i výstupu (zejména HTML, JavaScript, URL)
- Používání Content Security Policy (CSP)
- Nepovolit nahrávání neošetřeného uživatelského obsahu

# W-1-16
## front
Jakými způsoby lze zvýšit bezpečnost autentizace uživatelů ve webových aplikacích?
## back
- Používat vícefaktorovou autentizaci (například kombinace znalosti, vlastnictví nebo biometrie)
- Využívat silná hesla a pravidelnou jejich změnu
- Omezit počet pokusů o přihlášení
- Šifrovat spojení mezi klientem a serverem (např. pomocí HTTPS)
- Pravidelně měnit a odvolávat API klíče

# W-1-17
## front
Jaký údaj se posílá v hlavičce HTTP při použití API klíče?
## back
- Klient posílá v HTTP hlavičce hodnotu API klíče, např. X-API-Key: {hodnota_tokenu}
