## back

# W-1-3
## front

## back

# W-1-4
## front
Jaký je typický životní cyklus úkolu nebo chyby v bug tracking systému? (Vypište v bodech)
## back
1. Zachycení (Reporting)
2. Přidělení (Assignment)
3. Analýza (Analysis)
4. Implementace (Implementation)
5. Testování (Testing)
6. Uzavření (Closure)
7. Reopen (případně)

# W-1-5
## front
Co zahrnuje fáze Zachycení (Reporting) v životním cyklu chyby?
## back
- Uživatel nebo vývojář zadá nový úkol/chybu
- Přidá popis, prioritu, kroky k reprodukci, případně přiloží screenshoty nebo logy

# W-1-6
## front
Vyjmenujte hlavní fáze, které nastanou po Zachycení (Reporting) úkolu až do jeho uzavření.
## back
- Přidělení (Assignment)
- Analýza (Analysis)
- Implementace (Implementation)
- Testování (Testing)
- Uzavření (Closure)

# W-1-7
## front
Co se stane, když se chyba v bug tracking systému po uzavření znovu objeví?
## back
- Chyba se znovu otevře (Reopen)
- Proces pokračuje dalším řešením chyby

# W-1-8
## front
Co je hlavní princip správy a sdílení zdrojových kódů, který zaručuje, že každá změna má svůj unikátní identifikátor?
## back
- Verzování (Versioning) – každá změna kódu je zaznamenána s unikátním commit hashem

# W-1-9
## front
Co umožňuje branchování ve správě zdrojových kódů?
## back
- Paralelní vývoj funkcí, opravy chyb nebo experimenty bez narušení hlavní větve (např. main nebo master)

# W-1-10
## front
Jaký je účel sloučení (merging) při práci se zdrojovým kódem?
## back
- Sloučení změn z jedné větve do druhé, často po schválení pomocí pull request nebo merge request

# W-1-11
## front
Vysvětlete, co je rebase a squash v kontextu správy kódu.
## back
- Rebase: úprava základny větve, změna pořadí commitů/history před sloučením do hlavní větve
- Squash: sloučení více commitů do jednoho, aby byla historie přehlednější

# W-1-12
## front
Jaký je účel code review a kdo jej provádí?
## back
- Mechanismus kontroly kvality
- Jiný vývojář posoudí změny před jejich začleněním do hlavní větve

# W-1-13
## front
Co znamená Continuous Integration (CI) a jaký má význam?
## back
- Automatizované testy a buildy při každé změně kódu
- CI podporuje včasné odhalení chyb a zajišťuje stabilní build

# W-1-14
## front
Popište princip Git Flow.
## back
- Main a Develop větve
- Feature branches pro nové funkce
- Hotfix branches pro opravy chyb

# W-1-15
## front
Jaký je rozdíl mezi Git Flow a GitHub Flow?
## back
- Git Flow: více větví (main, develop, feature, hotfix)
- GitHub Flow: jednoduchý model s main větví do které se mergují feature větve

# W-1-16
## front
Co kombinuje GitLab Flow a čím se liší od ostatních?
## back
- Kombinuje Git Flow a GitHub Flow
- Navíc má stage branches pro různé fáze nasazení

# W-1-17
## front
Jak funguje Trunk Based Development?
## back
- Všechny změny se provádějí přímo na hlavní větvi
- Časté commity podporují rychlý rozvoj a integraci změn

# W-1-18
## front
Vyjmenujte hlavní přínosy správy a sdílení zdrojových kódů v týmu.
## back
- Zaznamenání všech změn s historií
- Možnost paralelní práce na různých funkcích
- Návrat ke starším verzím kódu
- Přehled o změnách a jejich autorech
- Automatizované testování a CI/CD

# W-1-19
## front
Které nástroje slouží nejen ke sledování chyb, ale jsou zároveň integrované s verzovacím systémem?
## back
- GitHub Issues / GitLab Issues – integrované systémy správy chyb a požadavků přímo v rámci verzovacích systémů
